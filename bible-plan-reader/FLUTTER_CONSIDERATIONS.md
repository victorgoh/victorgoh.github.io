# Future Considerations: Migrating to a Flutter Mobile App

This document outlines the architectural blueprints, future implementation ideas, and security challenges for migrating the Bible Reading Plan & Daily Prayer Guide SPA into a cross-platform native mobile application (iOS & Android) using Flutter.

---

## 🛡️ The Core Security Challenge: Safe, Verified Content Repositories

In a decentralized system where churches host their own JSON plan files, allowing a mobile app to connect to arbitrary server endpoints via scanned QR codes introduces major safety risks:

1. **Malicious Content Injection**: A rogue endpoint could serve JSON files loaded with phishing links, offensive text, or redirect buttons targeting malicious sites.
2. **Denial of Service (DoS) Crash Loops**: Malformed JSON payloads can easily crash typed JSON deserializers in Dart if not strictly sanitized.
3. **Data Harvesting**: Pointing the app to a tracking server exposes the user's IP address, device metadata, and reading schedules.

### Proposed Solutions for a "Safe & Verified" Network Infrastructure

To keep the application secure and trustable, the Flutter app should implement the following three-layer defense:

```
[QR Scanned URL]
       │
       ▼
 1. HOST DOMAIN FILTER ➔ (Matches whitelist? e.g., GitHub Pages, Cloudflare Pages)
       │
       ▼
 2. SCHEMATIC CHECKER  ➔ (Does JSON structure parse safely without typing errors?)
       │
       ▼
 3. SIGNATURE VERIFIER ➔ (Does the file contain a valid SHA-256 cryptographic signature?)
       │
       ▼
[Cache & Load Plan]
```

#### Layer 1: Trusted Host Filtering (Whitelisting)
By default, block arbitrary IP addresses or unknown domains. Limit custom repositories to known, secure, and standardized static hosting providers where code execution is impossible:
*   **Allowed Domains**: `*.github.io` (GitHub Pages), `*.pages.dev` (Cloudflare Pages), `*.web.app` / `*.firebaseapp.com` (Firebase Hosting), `*.s3.amazonaws.com` (Amazon S3).
*   Churches hosting on self-managed servers must apply to have their domain whitelisted in a central index database, or manually override the security block in the settings with a warning prompt.

#### Layer 2: Cryptographic Content Signatures
To guarantee that a JSON file was actually generated by the verified church administrator and has not been intercepted or modified (Man-in-the-Middle attack):
*   **Public/Private Key Pair**: The church content creator signs their `plans.json` file using a private key when uploading the plan. This adds a `"signature"` metadata node at the bottom of the JSON.
*   **In-App Verification**: The Flutter app contains the church's public key (retrieved from the scanned QR code or verified directory). On startup, the app checks the hash of the JSON content against the signature node using the `pointycastle` or `cryptography` Dart package. If the hashes do not match, the app flags the content as tampered and refuses to load it.

#### Layer 3: Type-Safe JSON Deserialization
Prevent app crashes caused by bad typing in custom JSON files:
*   Use code generation tools like `freezed` or `json_serializable` in Flutter.
*   Enforce a try-catch deserializer helper that filters null values, truncates extremely long text segments to prevent overflow attacks, and enforces default fallback values for optional parameters.

## 🚀 App Startup & Repository Registration Lifecycle

When the user launches the app, the startup lifecycle must handle network states, custom domains, and cached resources seamlessly:

```
                  [App Launch]
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
    [Has Cached Plan]    [No Cached Plan]
             │                   │
    Render Offline UI            │
             │                   ▼
   Bg Sync Repository     Show Welcome Screen
   (Check ETag / version)        │
             │             ┌─────┴─────┐
      (New Version?)       ▼           ▼
       ┌─────┴─────┐  [Scan QR]   [Select Global]
       ▼           ▼       │           │
   Download     Do Nothing │           │
   & Verify                ▼           ▼
                       [Run Verifier Component]
                                   │
                                   ▼
                         [Active State Loaded]
```

1.  **Stage 1: Local Bootstrapping**: Read the active repository URL, preference configurations, and calendar checklists from local storage.
2.  **Stage 2: Offline-First Rendering**: Instantly render the last cached day configuration. The user should never stare at a loading screen if they are offline.
3.  **Stage 3: Repository Handshake**: Send an asynchronous background request (`If-None-Match` HTTP header using `dio`) to check if the repository's `plans.json` has changed.
4.  **Stage 4: Custom Scan Handler**: When scanning a new QR code:
    *   Verify the URL format.
    *   Fetch target `plans.json` to verify schema.
    *   Prompt user: *"Do you want to switch your church provider to Hope Fellowship?"*
    *   On confirm, overwrite storage keys and reload state.

## 📦 Mobile Storage Architecture

Browsers restrict `localStorage` to a volatile 5MB limit. Mobile platforms provide robust databases for an offline-first experience:

*   **Isar Database (Recommended)**: A fast, type-safe NoSQL database for Flutter. Perfect for storing plan registries, parsed scripture text, and completed items lists.
*   **Secure Storage**: Use `flutter_secure_storage` (Keychain on iOS, AES-encrypted SharedPreferences on Android) to store sensitive configurations, preferences, or private keys.
*   **Media Caching**: Integrate the `cached_network_image` package to download and save devotional header images. Add a "Download Audio for Offline Use" toggle that caches devotional MP3 sermonettes directly to the device directory.

## 💡 Future UX/UI Mobile Integrations

Migrating to Flutter unlocks native mobile OS capabilities that improve engagement:

1.  **Lock Screen & Home Screen Widgets**:
    *   Display the current day's scripture passage and checklist status directly on the user's home screen.
2.  **Native Audio Playback Integrations**:
    *   Implement `audio_service` so devotionals can be listened to in the background, showing playback progress, pause/play triggers, and lock screen controls.
3.  **System Sharing Intent**:
    *   A native share button that formats text reflections or scripture passages with a pre-configured link, allowing users to send them directly to WhatsApp, Telegram, or their favorite notes app.
4.  **Quiet Time Push Notifications**:
    *   Local scheduled notifications reminding the user to complete their daily reading at their preferred hour (e.g., 7:00 AM daily), even if the app is closed.

## 🌐 Flutter Web vs. React/Vite SPA Comparison

If we were to implement the SPA web target using Flutter Web instead of our current React/TypeScript stack, here is how the two approaches compare:

### Comparison Matrix

| Feature / Criteria | React + TypeScript SPA (Current) | Flutter Web (Dart) |
| :--- | :--- | :--- |
| **Initial Load Speed** | **Excellent**: Bundle is ~215KB JS / ~18KB CSS. Loads in under **200ms**. | **Poor**: Downloads the entire WebAssembly engine (~2MB to 5MB). Takes **2 to 5 seconds** on a splash screen. |
| **Text Selection & Sharing** | **Perfect**: Native HTML elements. Users can naturally highlight paragraphs to copy and paste to external journaling apps. | **Limited**: Renders text on a canvas. To allow text selection, developers must wrap widgets in a specific `SelectableText` component, which can feel clunky on mobile browsers. |
| **Code Sharing (Mobile App)** | **Low**: Requires wrapping in Cordova/Capacitor, or rewriting the UI layer completely for native mobile apps. | **Excellent**: 100% of the UI code is shared. You build once and output iOS, Android, and Web builds simultaneously. |
| **SEO & Discoverability** | **Good**: Semantic HTML elements can be indexed by search engines. | **None**: The DOM is rendered as a canvas; search engines see it as a single empty canvas element. |
| **UI Polish & Animations** | **High**: Requires manual CSS transition bindings. | **Out-of-the-Box**: Extremely fluid native gestures, physics-based scroll, and hero transitions. |

### Hosting Comparison on Static Sites (GitHub, Cloudflare, Firebase)

Both frameworks compile to pure static assets and can be hosted just as easily on the recommended platforms. 

#### Flutter Web Deployment Steps:
1. Compile the build: `flutter build web --release`
2. Push the contents of the `build/web/` output folder to the target server.
3. *Note*: For GitHub Pages (which hosts on subdirectories, e.g. `username.github.io/repo-name/`), you must specify the base path during compile: `flutter build web --base-href "/repo-name/"`, otherwise the Javascript assets fail to load.
